# Bridge dla Agrowca — dokumentacja, audyt i plan odbudowy

Aplikacja do konsolidacji cenników opon rolniczych od 10 dostawców (MO1–MO10):
normalizuje dane do wspólnego modelu produktu, pozwala zatwierdzać zmiany
i eksportuje katalog do sklepu (Selly / Shoper).
Produkcja: **panel.agritires.eu**, serwer `/home/admin/private_apps/bridge/`.

> **⚠ Kluczowe ustalenie audytu:** ani backend, ani frontend **nie mają kodu
> źródłowego**. Wszystko w repozytorium to artefakty buildu — zminifikowane bundle
> bez sourcemap. Potwierdza to niezależnie baza wiedzy (§6). Skala i konsekwencje: §2.
> Plan wyjścia: **§9**.

## 1. Stos technologiczny

### Backend

| Warstwa | Technologia |
|---|---|
| Runtime | Node.js ≥ 18, CommonJS (`.cjs`) |
| Framework HTTP | Express (wbudowany w bundle) |
| ORM | **Drizzle ORM** (wbudowany w bundle) |
| Baza danych | SQLite przez `better-sqlite3` ^11.7 (WAL), plik `data.db` |
| Autoryzacja | JWT + cookie `bridge_session`, hasła `bcrypt` |
| Upload | `multer` (memory storage, limit 50 MB) |
| Parsowanie | `csv-parse` ^5.5, `xlsx` ^0.18, `exceljs` ^4.4, `iconv-lite` ^0.6 |
| Konfiguracja | `dotenv` ^16.4 (`.env` tylko na produkcji) |
| Deploy | PM2 (`ecosystem.config.cjs`), fork, `--max-old-space-size=2048` |
| Integracje | Selly.pl REST (OAuth2), Agrorami Magento 2 GraphQL |

`package.json` deklaruje tylko 6 pakietów — Express, Drizzle, JWT, bcrypt, multer
są **wkompilowane w bundle**. `archiver` jest ładowany dynamicznie, ale **nie
figuruje w `package.json`**.

### Frontend

| Warstwa | Technologia |
|---|---|
| Framework | **React 18** (SPA, `<div id="root">`) |
| Router | **wouter** |
| Komponenty | **Radix UI** (34 prymitywy w CSS, 103 odwołania w JS) — sygnatura **shadcn/ui** |

# na VPS, w katalogu assets/
for b in *.bak* *.backup-*; do
  orig="${b%%.bak*}"; orig="${orig%%.backup-*}"

done | sort

mapę funkcji, których brakuje w instrukcji v5.

### 6.2 Reguły biznesowe utrwalone w wiki

Rzeczy, których **nie da się wyczytać z kodu** — a są krytyczne przy przepisywaniu:

**Model danych i tożsamość produktu**
- EAN jest kluczem między dostawcami, gdy poprawny; `kod_importu` grupuje ten sam
  produkt w wielu magazynach, zachowując odrębne wiersze, stany i ceny.
- Podkreślnik w kodach Bridge (`MO9_336320`) rozwiązuje kolizje między dostawcami —
  **nie wolno go cofać**; 2 174 rekordy w Selly mają stare kody bez podkreślnika.
- MO9: `sku` Agrorami to widoczny kod dostawcy, ale **Magento `entity_id` jest
  stabilną tożsamością techniczną** — inaczej synchronizacja tworzy duplikaty.

**Ochrona danych ręcznych**
- `manual_overrides`, `nazwa_pamiec`, `waga_pamiec`, pamięć EAN i pamięć linków
  zdjęć utrzymują ręcznie potwierdzone wartości po kolejnych importach.
- Import **nigdy** nie nadpisuje istniejącego `link_zdjecia` wartością pustą.
- Import uzupełnia `zastosowanie` **tylko w pustych polach**.
- Słowniki atrybutów są kontrolowane: importy nie zasiewają `atrybuty_wartosci`
  automatycznie — nowe wartości idą przez kolejkę pending (akceptuj / edytuj /
  aliasuj / odrzuć).

**Reguły parserów (branżowe)**
- DOT pozostaje literalne; dwucyfrowe lata Grasdorf dostają prefiks `20`.
- Dętki są odrzucane; `inne` mapuje się zwykle na rolnicze.
- `szerokosc` = **pierwsza liczba rozmiaru w oryginalnej jednostce**, bez
  przeliczania cali na milimetry.
- Kategorie mają **pięć form kanonicznych**: Rolnicze, Ciężarowe, Przemysłowe,
  Leśne, Rolnicze małe.
- Wyjątki per dostawca: YARDMASTER, FARMPRO, Handlopex.
- Znaczniki `VF/IF/SB/HF/LF/TL/TT` wydobywane z nazwy lub pól źródłowych.

**Ceny**
- Cena sprzedaży = cena zakupu → reguły narzutu → VAT; **promocje to osobna
  warstwa po marży**. Pozornie ujemna marża może wynikać z aktywnej promocji.

**Agrorami / MO9**
- Stan czytany z `stock_availability.in_stock_real`, **nie** `in_stock`.
- Wartości z sufiksem plus (`5+`, `15+`) to **dolne granice** — trzeba zapisać
  surową wartość i wyznaczyć `stan_min`.
- Stary publiczny CSV Agrorami miał błędne stany — dlatego przejście na GraphQL.

**Selly**
- Marki idą przez natywną encję producenta (`producer_id`), nie jako atrybuty.
- Cena, stan, EAN, waga, kategoria = pola systemowe produktu, nie filtry.
- `Dostawca` / MO1–MO10 to atrybut **wewnętrzny, niefiltrowany**.
- API Selly odrzuca literalne `0` jako pustą wartość.
- Symbole Unicode (`✓`) są czytane jako zwykły tekst — trzeba zamienić na `tak/nie`.

## 8. Ustalenia audytu

### Krytyczne

1. **Brak kodu źródłowego dla całej aplikacji.** Backend: 42 endpointy w
   zminifikowanym bundlu. Frontend: 100% niedostępny. Potwierdzone niezależnie
   przez bazę wiedzy (§2.2).

2. **Ręczne łatanie zminifikowanych bundli — po obu stronach.** Backend:
   8 skryptów `patch_*.cjs`. Frontend: `index-CX3ki01.js` to ręcznie edytowana
   i ręcznie nazwana kopia buildu Vite. Nazwa `index.cjs.v6_routesorder_bad`
   dowodzi, że raz już poszło źle.

3. **Brak kontroli wersji.** Nie jest to repozytorium Git. Baza wiedzy zgłasza
   ten problem od czerwca (*„no Git repo"*, *„move toward a private Git repository"*).

4. **`JWT_SECRET` z zahardkodowanym fallbackiem** — `"bridge-agrowiec-secret-2026"`.
   Baza wiedzy **trzykrotnie** wnosi otwarty punkt *„rotate exposed VPS/SSH/JWT-style
   secrets"* — do dziś niezrealizowany.

5. **CORS odbija dowolny `Origin` z `Allow-Credentials: true`**, cookie
   `SameSite=None; Secure` na sztywno. Brak ochrony przed CSRF.

6. **Zerwany kontrakt API klient ↔ serwer.** Klient woła `/api/attributes`
   i `/api/attribute-kinds`, których backend nie ma. Widok Atrybuty działa na
   IndexedDB, a produkcyjnie jest przykrywany 50-kilobajtowym skryptem (§5.4).

7. **Dryf schematu: 4 tabele i 2 kolumny istnieją tylko w produkcji** (§3.3).
   Czysta instalacja nie wstanie.

### Poważne

8. **Cztery odrębne warianty bundla backendu** o różnych MD5. Nie wiadomo, który
   odpowiada któremu stanowi źródeł.

9. **~40% API nie ma interfejsu.** 31 endpointów analityki — zero UI. 8 endpointów
   Selly — UI istnieje, trasy nie. Import v6, paginacja, overrides, audit-log — bez UI.

13. **Ścieżka `/home/admin/private_apps/bridge/` zahardkodowana w 115 plikach**,
    w tym w modułach runtime.
