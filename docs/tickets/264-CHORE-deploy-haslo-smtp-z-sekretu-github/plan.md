# 264 — wdrożenie produkcji przekazuje hasło SMTP z sekretu GitHub

Prośba użytkowniczki 2026-10-14: zamiast ręcznego wpisu hasła do `.env` na serwerze — sekret w GitHubie, który wdrożenie samo zaniesie na serwer.
Ograniczenia, które to wyznaczyły: GitHub nie pozwala odczytać sekretu nikomu poza workflow (więc nie „czytam go z repo”); na serwerze klucz SSH ma wymuszone jedno polecenie (`deploy-produkcja.sh`), więc hasło nie może być argumentem polecenia; hasło nie może trafić do repozytorium (publiczne) ani do listy procesów/logów.
Rozwiązanie:
- Workflow `deploy-produkcja.yml`: sekret `SMTP_MAIL_INFO_PASSWORD` (Settings → Secrets and variables → Actions) idzie przez `env:` (GitHub maskuje wartość w logach) i **na STDIN** polecenia SSH (`printf … | ssh …`; `printf` to builtin — brak w liście procesów). Brak sekretu = pusta linia = nic się nie dzieje.
- `tools/przyjmij-sekret.sh` (źródłowany przez `deploy-produkcja.sh` zaraz po wczytaniu `.env`): czyta jedną linię ze stdin (tylko gdy stdin to nie terminal), porównuje z `SMTP_HASLO` w `.env`; gdy inne — zapisuje `SMTP_HASLO=…` (cytowane `printf %q`, więc `source` czyta bez błędu), zachowuje pozostałe linie i prawa pliku (0600), eksportuje hasło i ustawia `FORCE=1` (serwer musi się przebudować/zrestartować, żeby backend wczytał hasło, także gdy commit się nie zmienił). Hasło nigdzie nie jest wypisywane.
- Test `deploy.przyjmij-sekret.test.ts` uruchamia funkcję w prawdziwym bashu: znaki specjalne, 0600, brak zmian przy tym samym haśle, zamiana starego, pusty stdin, brak pliku.
Zmiana ścieżki produkcyjnej (`deploy-produkcja.sh` + workflow): ⚠ **działa dopiero od DRUGIEGO wdrożenia po merge'u** (skrypt aktualizuje się w trakcie, a pierwsze wdrożenie biegnie starą wersją skryptu, która ignoruje stdin). Po merge'u do `main`: drugie wdrożenie = Actions → „Deploy produkcja” → „Run workflow” (nie wymaga nowego commita dzięki FORCE=1 przy nowym haśle).
Wymaga od użytkowniczki: dodać sekret `SMTP_MAIL_INFO_PASSWORD` w GitHubie (Settings → Secrets and variables → Actions; jeśli środowisko `produkcja` ma własne sekrety — tam). Hasło ręcznie wpisane w `.env` zostanie zastąpione wartością z GitHuba przy pierwszym wdrożeniu z sekretem. `deploy-staging.sh` bez zmian — środowisko testowe nie wysyła poczty.

Nazwa sekretu: użytkowniczka dodała w GitHubie sekret `SMTP_MAIL_INFO_PASSWORD` (2026-10-14), więc workflow i dokumentacja używają TEJ nazwy (pierwotnie planowane `PROD_SMTP_HASLO`).
